# 深大校园网疑云：为什么我连路由器的时候，官方登录应用失败了？

> 上一篇写了 `ac_id` 是什么、我们自己的工具为什么挂在它上面。
> 这篇换个角度：**把官方客户端拆开，看它到底死在哪一步。**
>
> 结论先放这儿：它没坏，也没有 bug。它是把「探测到校园网认证页」这件事，
> 押在了三个固定网址上；而接了路由器之后，这三个网址**一个都不再经过那栋楼**。

---

## 零、现象

前置条件：电脑不直接插墙口，而是接在自己的路由器后面。

结果是两个一起挂：

- 官方「上网认证客户端」起不来（一直转圈，最后弹一个让你手填地址的框）
- 我们自己的工具也登录不上

但手动打开这个网页，能正常登录：

```
https://net.szu.edu.cn/srun_portal_success?ac_id=12&theme=proyx
```

注意那个 `ac_id=12`。这个是上一篇的主角，这次只当作已知条件。

---

## 一、先看这个应用是什么

先确认它不是个黑盒。安装目录看着很眼熟：

```
上网认证客户端.exe        154 MB
resources/app.asar        94 MB
chrome_100_percent.pak
icudtl.dat
libGLESv2.dll
...
```

标准 Electron 打包。**它是网页写的**，界面就是 HTML/CSS/JS。

`app.asar` 没有加密，也没有字节码保护，纯文本。直接解：

```python
import struct, json
f = open(r'C:\Program Files\上网认证客户端\resources\app.asar', 'rb')
f.seek(12)
header_size = struct.unpack('<I', f.read(4))[0]
index = json.loads(f.read(header_size).rstrip(b'\x00').decode('utf-8'))
# index 是文件树，每个叶子带 offset / size，数据区从对齐后的位置开始
```

3496 个文件，源码、依赖、图片全在里面。后面要用的两个文件：

- `config.js`（31 KB）—— 界面配置
- `assets/ipoe.544386e8.js`（6 KB）—— 自动发现逻辑

---

## 二、第一个疑点：配置里只有一种接入点

`config.js` 长这样：

```js
window.CONFIG = {
    global: {
        checkOnlineWithIP: false,
        urlIPField: 'wlanuserip',
        // ...
    },

    // ACID
    1: {                     // ← 注意这个 key
        desktop: { /* 桌面端配置 */ },
        mobile:  { /* 移动端配置 */ },
    },
}
```

**顶层 key 只有一个：字面量 `1`。**

注释把那行写得很明白：`// ACID`。

也就是说，这份客户端里**只带了一套 `ac_id=1` 的配置**。整套界面（按钮文案、认证方式、显示哪些信息、风格颜色）全都挂在这个 key 下面。

这一眼看上去像是死因。但先别急——一个成熟的商业客户端不可能连"用户可能在别的接入点"都没考虑。继续挖。

---

## 三、关键：`ac_id` 是**运行时探测**出来的

翻主进程代码，找到一个属性定义：

```js
// node_modules/@portal/core/dist/attribute.js
this.acid = options.acid;
```

`acid` 是从构造函数参数传进来的，**不是从 `config.js` 里那个 key 读出来的**。它有独立的来源。

顺着 `options.acid` 往上追，追到了真正干活的文件 `@portal/electron/dist/ipoe/index.js`：

```js
getPortalInfo(url) {
    return promiseAny([
        this.createPortalView('http://auth.srun4k.com'),
        this.createPortalView('http://1.1.1.1'),
        this.createPortalView(url).then(),
    ], this.timeout);   // timeout = 3000
}
```

思路完全正确，而且和我们后来做的一模一样：**开一个隐藏浏览器窗口去访问这几个地址，看看会不会被网关拦下来。** 被拦就说明在校园网闸门后面，然后从跳转地址里把 `ac_id` 读出来。

再看它怎么判断"拦下来了"：

```js
view.webContents.on('did-finish-load', async () => {
    const url = view.webContents.getURL();
    const isPortal = url.includes('srun_portal') && url.includes('ac_id');
    if (!isPortal) return;                          // ← 没被拦，直接返回

    const portalURL = new URL(url);
    const searchParams = new URLSearchParams(portalURL.search);
    searchParams.set('theme', 'app');
    portalURL.pathname = '/srun_portal_pc';

    const response = await node_fetch(portalURL.href, { /* ... */ });
    const $ = cheerio.load(await response.text());

    success({
        authURL: portalURL.origin,
        config: {
            acid: JSON.parse($('#acid').html()),     // ← 从页面里读真实 acid
            ip:   JSON.parse($('#ip').html()),
            nas:  JSON.parse($('#nas').html()),
            // ...
        },
    });
});
```

判据是**两个字符串同时出现在 URL 里**：`srun_portal` 和 `ac_id`。

设计得很聪明——它不猜，而是问网关。**问题在于它问了谁。**

## 四、三个探测网址，接路由器后全军覆没

渲染层传进去的那个 `url` 参数（源码里的 `L`）：

```js
const L = "https://net.szu.edu.cn";
```

所以真正会去试的三个地址是：

| # | 地址 | 意图 |
|---|---|---|
| 1 | `https://net.szu.edu.cn` | 深大认证门户 |
| 2 | `http://auth.srun4k.com` | 深澜厂商的通用探测域名 |
| 3 | `http://1.1.1.1` | 一个"只要上网就一定能通"的地址 |

看起来覆盖得挺全。**但接入路由器之后，这三个全部失效。**

我在当前网络下实测了一把：

```
=== https://net.szu.edu.cn
   302 -> https://net.szu.edu.cn/index_1.html

=== http://auth.srun4k.com
   400 Invalid URL   (Akamai 边缘节点直接拒绝)
   
=== http://1.1.1.1
   TimeoutError: timed out
```

一个个看：

**第 1 个，认证门户自己。** 它 302 到的地址是 `index_1.html`——门户首页，**地址里没有 `ac_id`**。所以 `url.includes('ac_id')` 这个判断不成立，`createPortalView` 收不到成功回调，会在 3 秒后超时失败。

这里有个必须点出来的细节：**门户首页那个默认入口是 `/srun_portal_pc?ac_id=1`，而它恰恰不在这条路径上。** 所以网上流传的"官方客户端写死了 `ac_id=1`"是不准确的——写死 1 的是门户*入口链接*的默认值，不是客户端的逻辑。客户端根本没走到那一步。

**第 2 个，厂商通用域名。** 在外网环境（比如宿舍自己的宽带）它本来能通，是个合理的兜底。但在深大这条只有校园网出口的线路上，DNS 解析之后流量出不去，撞上 Akamai 的边界节点被拒，直接 400。它不是跳转，连"页面"都没返回。

**第 3 个，`1.1.1.1`。** 这个地址的意图是"随便访问个外网看看会不会被拦"。但问题在于：接路由器的情况下，**它压根不是校园网网关要拦的目标，或者流量根本出不去**——实测直接超时。

三个都失败。而且注意总超时是 **3 秒×3**，加上重试，用户看到的就是"卡半天然后弹框"。

## 五、最后的兜底：弹框让你手填

渲染层的重试逻辑（`assets/ipoe.544386e8.js`，已格式化）：

```js
async getAuthInfoByAuto() {
    let retry = 0;
    return new Promise((resolve, reject) => {
        const attempt = () => {
            window.ipc.invoke('/portal/ipoe/init/auto', L)
                .then(data => { this.initIPoEPortal(data); resolve(); })
                .catch(() => {
                    retry += 1;
                    retry < 3 ? attempt()      // 不到 3 次就再试
                              : (this.showIPoEInit = true, reject());  // 否则弹手动输入框
                });
        };
        attempt();
    });
}
```

`showIPoEInit = true` 就是把那个「请输入认证地址」的输入框显示出来。

所以完整流程是：

```
开机
 └─ 自动探测三个固定网址
     ├─ 成功 → 从跳转地址拿到真实 ac_id，正常认证
     └─ 三个都失败
         └─ 重试（总共 3 轮）
             └─ 还失败 → 弹框：请输入认证地址
                 └─ 用户懵：填啥？
```

**用户看到的是"应用起不来"，实际是"自动发现失败后进入手动模式"。** 它没崩，它一直在等你填那个地址。

那个要填的地址是什么？就是开头那个：

```
https://net.szu.edu.cn/srun_portal_success?ac_id=12&theme=proyx
```

——但普通用户怎么可能知道这个。他甚至不知道 `ac_id` 是什么。

## 六、为什么路由器会让这三个网址失效

把上面串起来，答案其实很朴素：

**这三个探测网址，本质上都在问同一个问题：「我现在是不是在校园网的闸门后面？」**

- 在宿舍/教学楼直接插墙口时，这个问题有答案：请求外网 → 网关把你拦下来 → 302 带 `ac_id`
- 接了自己的路由器之后，**探测发出去了，但那条路径不再经过校园网的认证闸门**

于是：

| 情形 | 网关行为 | 客户端读到什么 |
|---|---|---|
| 直插墙口、未认证 | 302 到带 `ac_id=12` 的认证页 | 成功 |
| 经路由器、未认证 | 无 302，或流量被丢弃/被上游拒绝 | 失败 ×3 |

客户端没有错。它做的每一步都对：探测、找 `ac_id`、失败重试、最后退到手动兜底。

**它只是没料到"探测请求可能根本不经过认证闸门"这一种网络形态。** 这个假设在它被写出来的场景里是成立的。

## 七、和我们的实现对照

有意思的是，我们自己的工具最初也挂在同一个地方，只是形式不同：

| | 官方客户端 | 我们（改之前） |
|---|---|---|
| ac_id 来源 | 运行时探测（三个固定网址） | **写死 1** |
| 探测失败 | 重试 3 次 → 弹框手填 | 静默用 1，认证失败 |
| 失败表现 | 「应用起不来」 | 「认证失败：ok 」 |

**官方那个是"探测失败"，我们那个是"压根没探测"。** 从用户视角看症状不一样，但病根是同一个：

> 都默认了「`ac_id` 要么固定、要么能从固定入口问出来」。

改完之后我们的取值链是这样的：

```go
func (c *SrunClient) resolveAcIDWithSource() (string, AcIDSource) {
    if c.AcID != "" {
        return c.AcID, AcIDSourceManual        // 1. 用户说了算
    }
    if c.lastAcID != "" {
        return c.lastAcID, AcIDSourceCache     // 2. 这张网上次成功过
    }
    if id := c.discoverAcIDFromRedirect(); id != "" {
        return id, AcIDSourceRedirect          // 3. 网关跳转，权威
    }
    if id := c.discoverAcIDFromPortal(); id != "" {
        return id, AcIDSourceGuess             // 4. 挨个试，猜的
    }
    return "1", AcIDSourceGuess                // 5. 最后兜底
}
```

两个关键改进，正好是官方那套里缺的：

**一是探测目标不能是认证门户自己。** 我一开始也把 `net.szu.edu.cn` 放进了探针列表，结果在线时它 302 到自己的登录页、带着默认 `ac_id=1`，让我"成功地"读出一个假的 1。必须**只认 3xx 跳转**（`resp.StatusCode/100 != 3 { continue }`），并且探针只用真正的外网点（`msftconnecttest` / `gstatic` / `apple`）。

**二是探测失败时不能只靠用户手填，而要按网络记住上次成功的值。** 缓存键用「默认网关 + 出口 IP」：

```go
func Egress() string { return NetKey(Gateway(), LocalIP()) }
```

因为 `ac_id` 跟**物理墙口**走、不跟设备走。同一台路由器插回原来的口，编号不变；换个墙口才变。网关地址恰好和这件事同步变化。

于是第二次之后就再也不需要探测了——包括在路由器后面这种"三个固定网址全失效"的场景。

## 八、小结

| 问题 | 答案 |
|---|---|
| 官方客户端坏了吗 | 没坏。探测失败后退到手动输入模式，用户以为是"起不来" |
| `ac_id` 写死 1 了吗 | 没有。它是运行时探测的（写死 1 的是门户入口链接的默认值） |
| 探测哪三个地址 | `net.szu.edu.cn` / `auth.srun4k.com` / `1.1.1.1` |
| 为什么接入路由器就全挂 | 探测请求不再经过校园网认证闸门，拿不到带 `ac_id` 的 302 |
| 判据是什么 | URL 里同时出现 `srun_portal` 和 `ac_id` |
| 失败几次后弹框 | 3 轮 |
| 正确的解法是什么 | 只认 3xx 跳转 + 按网关缓存上次成功的 `ac_id` |

这题最有意思的地方在于：**它不是 bug。** 它是三个"在这个网络形态下成立"的合理假设，撞上了一个它们都没覆盖的情况。

而那三个地址里，第一个是**认证门户自己**——这是最反直觉的一点。直觉上"断网了就去访问认证门户"，但在接入路由器这种场景里，门户恰恰是唯一一个**永远不可能**告诉你真实 `ac_id` 的地方。

它只能告诉你它自己是谁（`ac_id=1` 的默认入口），告诉不了你在哪。
