- 已发布基线是 **beta0.8.0**，PR #8 已合并（`faf22af`）；Windows Electron 安装、重开、便携引擎共存、同版本重装和卸载通过发布 CI，见第 45 节。

- 安装版关主窗口后宠物与托盘继续运行；从宠物或托盘重开，完整退出使用托盘或设置。便携版保持所有窗口关闭约 10 秒退出。
- 真实学校账号验收仍未完成：2026-09-26 校历官网可达，但教务、认证与 WebVPN 连接失败。不同培养层次、琴房账号权限及预约流程不能由模拟接口通过来代替。
- 当前待办只维护在**第 32 节**；历史阶段记录不代表当前完成状态。README 中英两版随每次更新同步。
- 保留像素校园、木框与纸张的视觉风格；庭院与学习存档在本机，校园卡号默认隐藏。实验 VPN 不随公开发行版构建，校内共享后端尚未部署。

## 2. 分类方法

| 维度 | 标记 | 含义 |
| --- | --- | --- |
| 重要程度 | P0 | 发布阻断：凭据/安全、未认证报成功、代码许可来源；相关功能对外发布前解决 |
| 重要程度 | P1 | 当前核心必修：正常操作、真实状态、内容可见、数据可靠；功能扩展前完成 |
| 重要程度 | P2 | 近期体验/功能：不阻断基础使用，但提高效率与价值 |
| 重要程度 | P3 | 长期或低频功能，先记录范围 |
| 难度 | S 容易 | 单点或少量文件、依赖明确、可本地回归 |
| 难度 | M 中等 | 多处联动、页面结构或数据层改造，需要跨页验证 |
| 难度 | L 较难 | 协议/平台/认证链路或外部证据依赖，需要专项验证 |

按 **P0/P1 × S → P0/P1 × M/L → P2 × S/M → 其他** 执行。难度不是工期承诺。
“已完成”须有验收证据；“部分完成”不关闭剩余范围；真实验证进展以第 14 节为准：已在学校官方 WebVPN 完成登录并查看场地时段；不等于校园网双协议认证已现场验收。

## 9. 校内服务器能承担哪些业务

可以将公共业务放在校内服务器，桌面本机服务继续负责账号凭据和网络认证。校内托管本身不会自动获得教务等系统的 API 权限，也不意味着校外用户可以直接访问该服务器。

| 业务 | 是否需要后端 | 优先/难度 | 建议方案与边界 |
| --- | --- | --- | --- |
| 官方服务目录、常用入口、应用版本清单 | 推荐 | P2 / S | 可先用静态 JSON + HTTPS；每项有来源、校区、更新时间，离线回退本地目录 |
| 学校公告、讲座、办事通知聚合 | 需要 | P2 / M | 定时抓取允许访问的公开来源，去重、缓存、搜索；保留原文链接与抓取时间，不复制整篇文章冒充原创 |
| 官方校历/考试周/公共地点资料 | 推荐 | P2 / S–M | 后台统一录入核实数据，客户端缓存；个人教学周仍能本地手动设定 |
| 公告关键词订阅、提醒收件箱 | 需要 | P2 / M | 用户选择订阅范围；首期应用内提醒，邮件/外部推送需单独选择，不默认发消息 |
| 跨设备庭院/待办同步 | 需要 | P3 / L | 自愿注册或授权登录，存档版本、冲突副本、删除/导出、备份与速率限制；不上传校园密码 |
| 反馈与崩溃上报 | 可选 | P2 / M | 用户主动提交，脱敏后预览；日志不含账号密码和会话 token，不默认采集 |
| 排行、访客、多人庭院、交易 | 需要 | P3 / L | 服务器校验经济规则与身份、反滥用和内容管理；初版不做 |
| 课表/成绩/余额/借阅 | 视接入方式 | P2 / L | 优先官方接口和明确授权；个人会话本地持有或可撤销短期票据，不替用户长期保管统一认证密码 |
| 校园网登录/注销、网络诊断 | 不应迁移 | P1 / M | 与使用者网卡/出口相关，留在本机执行；后端不能代表用户的网口完成认证 |

**首期架构**：HTTPS 反向代理 → 一个只读公共 API 服务 → SQLite/轻量数据库与定时采集。个人账户出现后再引入会话和按用户隔离的数据表，避免一开始做过大的后台。可使用 Go 与现有代码统一；数据库定期备份并演练恢复。

**首期接口建议**：`GET /v1/catalog`、`GET /v1/notices?source=&cursor=`、`GET /v1/calendar?term=`、`GET /v1/releases/latest`、`GET /healthz`。响应含 schemaVersion/source/updatedAt，ETag 与过期缓存；数据源采用允许列表，不提供任意 URL 转发。创建订阅和同步接口等到认证方案确定后单独接入。

**部署前仍需确定**：校内主机与域名、HTTPS 证书、允许的外网访问方式、服务运行用户/备份位置、公开数据源授权与抓取频率。当前没有这些部署信息，因此没有擅自创建远程服务，也没有假称后端已经上线。

### 14.2.1 共同瓶颈：本机尚未持有可复用登录会话

上表中 **C28（实时空位 / 预约）、C2（成绩在线读取）、C27（图书馆业务）不是各自独立的活**，
它们卡在同一个地基上：

- 当前只有**用户在浏览器里登录后的页面**能看到数据。官方页面登录成功
  **不等于**本机应用取得了可复用的会话或接口权限（见 14.1）。
- 本机既没有会话，也没有那些接口的**真实请求样本**（返回结构、字段、分页、权限差异
  都是未知）。此时写解析器只能靠猜，猜出来的东西会**报“成功/空位”但不真实** ——
  直接违反本项目的发布红线。
- 因此这三项在会话桥打通前不做，也不在发布说明里暗示已接通。

下一步若要推进，按这个顺序，且每一步都要有真实样本：

1. **会话桥最小验证**：用户自己登录后把会话交给本机（只存本机加密，不进源码、不进发布包），
   验证能用它重复取到同一份页面。账号密码与验证码始终不落地。
2. **抓一个真实只读请求**：确认时段数据到底是 HTML 渲染还是 JSON，弄清字段与分页。
3. **先只做查询**：写解析器并验证会话过期、无权限、无空位、断网四种情形都报错而不误报成功。
4. **预约提交最后做**，且属于写操作：必须由用户确认场地与时间后提交，失败不能报成功。
   在项目「不代替用户提交」的原则下，这一项始终要人亲自点确认。

## 15. 学校系统会话桥与在线成绩读取（2026-09-19）

用户授权参考 [tools4szu](https://github.com/MattDong123/tools4szu)（作者 Matt，深大校友，用于学术交流），
本轮把它的**接口事实**（URL、字段名、认证形态）用于实现，代码为 Go 重写，未复制其源码。

### 15.1 会话接入方案与待验证边界

§14.2.1 判定 C28/C2/C27 卡在「本机没有可复用登录会话 + 没有真实请求样本」。
参考项目提供了接口线索，但没有替代本项目的真实账号验收：

- 教务（`jwapp`）、研究生（`gsapp`）、场馆预约（`qljfwapp`）在同一 `ehall.szu.edu.cn` 主机下，存在复用登录会话的可能。
  Cookie 路径和账号业务权限可能不同，必须分别验证；社区静音舱位于另一站点，不能据此关闭 C28。
- 它的认证方式极朴素：**用户自己登录后，把浏览器里的 Cookie 交给程序**，不做登录逆向、
  不复现二次验证。该方案尚需验证不同业务的 Cookie 范围和真实返回数据。

因此调整为：**先做会话地基（粘贴 Cookie → 本机加密 → 复用 → 过期明确报错），
WebView 交互（D2）降级为后续「多一种获取方式」，不阻塞当前进度。**

### 15.2 本轮实现

| 项 | 位置 | 说明 |
| --- | --- | --- |
| 会话存储 | `internal/credential/session.go` + 三端 keyring | Windows DPAPI / macOS 钥匙串 / Linux Secret Service；安全存储不可用时拒绝保存，不降级为明文；与校园网密码分开存 |

### 15.3 安全与诚实性约束（已进回归）

- 会话**不落明文盘**、不进日志、不进源码、不进发布包；状态接口**只回报长度不回报内容**。
- 保存后立即清空输入框；清除会话**不影响校园网账号密码**（两者独立，有测试焊死）。
- **读不到 ≠ 没有数据**（本项目红线）：会话失效返回明确的 401 提示；服务端返回了行但认不出
  课程字段时**报错并让用户去官方核对**，绝不显示成「暂无成绩」。四种情形各有测试。
- 只读。不代提交预约、不代评教；参考项目里的自动签到与自动选课**明确不搬**（违反本项目原则）。

## 19. 出口已被占用时的提示修复（2026-09-20）

起因：用户在教学区网络上点登录，看到「这个网络出口已经有账号在线了，本次登录没有生效」，据此认为登录失败、上不了网。

### 19.1 实测结论：那次登录其实生效了

直接向深澜门户的 `rad_user_info` 发只读查询（绕开本项目的客户端，避免被自己的解析逻辑误导），拿到的事实：

- `error: "ok"` —— 这个出口当时已处于已认证状态。
- 会话 `add_time` 就在用户操作的那一分钟内，`keepalive_time` 与查询时刻只差几秒 —— 会话是活的。
- `online_device_total: "1"`，`online_device_detail` 里那台设备上报的 `os_name` 是 `Mac OS`。
- 而 `Mac OS` / `Macintosh` 正是本项目登录请求里上报的参数（见 `srun.go` 的 `os` / `name`），所以那个在线会话就是本次登录建立的。

也就是说：**用户全程在线、能上外网**，只是被工具的提示误导了。

### 19.2 三个真实缺陷

1. **把"没生效"报成了成功**。`error: "ok"` + `suc_msg: "ip_already_online_error"` 被当成认证成功返回（`OK: true`），却又配了一句「本次登录没有生效」——同一句话里既说成功又说没生效。
   关键在于深澜的 **IP 级短路**：这个出口已有会话时，服务端在校验账号密码和 `ac_id` **之前**就返回了。它既没验证过这组凭据，也没验证过这个接入点编号。

2. **把没验证过的 `ac_id` 写进了缓存**。既然服务端是在校验 `ac_id` 之前短路的，这个编号就没有被证实过；缓存它会让用户下次在别的网络里拿着错值去认证，反而更难查。

3. **能上外网时反而跳过在线查询**。命令行与桌面界面各写了一份相同判断，理由是"不需要认证"。但用户问的是"我到底登上了没"，而"能上网"恰恰是已登录的最强证据。跳过查询的结果是一句干巴巴的"没查到"，用户以为掉线，跑去反复点登录，然后被 `ip_already_online` 挡回来——正好掉进最让人困惑的那个状态。
   附带问题：两处都把查询错误用 `_` 吞掉了，用户连为什么"没查到"都看不到。

### 19.3 修复

- `Login()`：`ip_already_online` 不再返回成功；提示改为能直接回答"我现在能不能上网"，并顺手查一次在线信息，把设备数、在线 IP 与设备描述带出来。
- `ac_id` 缓存：只在认证真正被服务端接受之后写入。
- 新增 `portal.QueryOnline()`，把"按区域查在线状态"收成**一处**，命令行与桌面界面共用（原先的重复实现已删除）。联网时两套协议都问一次——`Detect()` 联网时会提前返回、没跑协议指纹，无从得知当初是哪套协议认证的——谁在线采信谁。
- `OnlineStatus` 增加在线设备数与设备描述；`status` 命令与 `/api/status` 在联网时也给出结论，查询失败时显示失败原因，不再笼统地说"没查到"。

### 19.4 验证

- **真实网络复现**：同一台机器、同一时刻，仅二进制不同 —— 修复前 `账号状态: 没查到`；修复后 `账号状态: 已在线` + 在线 IP + `在线设备: Mac OS · ...`。
- 新增测试 8 项：出口被占用不报成功且不写缓存；账号自身在线仍算成功且正常缓存；在线设备字段解析（含「JSON 字符串里再套一层 JSON」的真实格式）；补充字段读坏不影响在线判断；`error` 字段是唯一在线判据（实测返回里没有 `user_name`）；联网时必须查询；深澜无结果时回落到宿舍区协议；校外不发起查询。
- `go test ./...` 全部通过，`go vet` 通过，Windows 构建成品冒烟全部通过。

### 19.5 遇到这条提示时该怎么办

先看工具给出的在线状态：

- **显示"已在线"且外网连通** —— 会话有效，不需要再登录。
- **想换成另一个账号** —— 必须先让出口上原有的会话下线；同一个出口 IP 只能挂一个账号。
- **"出口被占用"同时外网也不通** —— 这才是真需要处理的：原来那个会话很可能已失效但没有释放。

不要在"已在线"的状态下反复点登录：每次都会走一遍 `ac_id` 探测，而且这次登录同样不会生效。

## 33. F21 修复：macOS 凭据不再经命令行参数暴露（2026-09-21，已随 beta0.7.1 发布；macOS 真机仍未验收，见 F25）

**问题**：darwin 的保存路径用 `security add-generic-password ... -w <密码 JSON>` 写入，
密码会出现在子进程的命令行参数里，同机其它进程 `ps` 就能看到。Windows 走 DPAPI、
Linux 早已改成只经标准输入，只有 macOS 这条漏着，而 `szunet-darwin-*` 是随发布分发的。

**依据**：Apple man page 对 `-w` 的说明是 "Put at end of command to be prompted (recommended)"，
即官方推荐让 `security` 提示输入，而不是把密码写进命令行。提示走 `readpassphrase(3)`，
它在打不开 `/dev/tty` 时会退回读标准输入。

**做法**（`internal/credential/keychain_prompt.go` + `nocontrollingtty_*.go`）：

1. 执行 `security add-generic-password -a <账号> -s <条目> -U -w`，`-w` 放最后且不带值；
2. 子进程脱离控制终端（`Setsid`）。否则命令行版在终端里跑时，子进程会去读用户的键盘，
   我们喂进去的管道没人读，保存会卡住等输入；
3. 密码连同换行从标准输入喂入；命令行参数里只有账号与条目名，没有机密；
4. **写前自检**：先用一次性条目（`szunet-selftest-*`）跑一遍「写 → 读回 → 比对 → 删除」，
   确认这条路在本机可用。自检不过就明确报错，绝不退回 argv 写法，也不碰用户的真实凭据
   （直接在真实条目上试错的代价是：万一没喂进去，留下的就是空值或错值）；
5. **写后校验**：读回比对，不一致就报错，不静默成功。自检结果只缓存成功——
   失败不缓存，用户解锁钥匙串后重试还能成功。

**验证**：

- 可移植测试 5 项（`keychain_prompt_test.go`，用假命令）：密码不进 argv、存入值与读回一致、
  自检条目用完即清、自检不可用时拒绝保存且不写真实条目、读回不一致必须报错、
  自检只在成功后缓存。本机 Windows 实测通过。
- unix 真命令测试（`keychain_prompt_unix_test.go`）：把 `securityBin` 指向假脚本，
  走真实 exec（含 `Setsid` 与标准输入管道），断言命令行参数里没有密码、
  值经 stdin 完整送达、且确实执行了读回校验。由 Linux CI 执行。
- 交叉编译 darwin / linux / windows 通过；`go vet`（含 darwin 目标）通过；
  Windows 成品重新构建后 74 项冒烟通过。
- **未验证**：真实 macOS 上 `security` 的提示输入是否确实读标准输入（`readpassphrase` 的退回行为）。
  若不成立，`szunet config set` 在 macOS 上会**明确报错**而不是静默泄漏——这是有意的取舍：
  宁可失败并让用户知道，也不要偷偷退回会被 `ps` 看到的写法。真机验收前不要把这条记成「已现场验证」。

### 35.2 抓到的缺陷：CLI 没账号时跳过在线查询（F22，已修）

- **现象**：同一台机器、同一时刻、同样没有保存账号——桌面端 `/api/status` 报 `online: true`，而 `szunet status` 报「账号状态: 没查到（没有可用的账号密码…）」。
- **原因**：`cmdStatus` 里是 `if credErr == nil { 查询 }`。门户查询本就按出口 IP 回答、与账号无关（桌面端正是这么调的），这个短路让没存账号的用户永远看不到在线状态——正是 F20 记录过的「用户只看到『没查到』而误判掉线」，当年桌面端修了、CLI 漏了。
- **修复**：去掉短路，`status` 与桌面端共用同一查询入口（新增 `statusOnline` 与可替换的 `queryOnline` 便于测试）；JSON 输出补 `online_known`；没账号且离线时补一句登录提示，但状态照报、不再拿「没查到」当结论。
- **验证**：新增 2 项 Go 测试（无账号仍查询、校外不查）；真实网络重跑——同一张网、同样无账号，修复后输出：

```
账号状态: 已在线
在线 IP : 172.27.47.91
在线设备: Mac OS · 172.27.47.91
```

### 35.3 仍需账号、只能由用户本人操作的验收

- **校园网真实登录 / 注销（教学区深澜）**：需要校园卡号与密码。当前出口已有一个在线会话，登录会命中 `ip_already_online` 分支——这本身就是对 F20 的现场验证（不得报成功、不得缓存 `ac_id`、应把在线设备信息带出来）。验收顺序建议：先在有会话时点登录看提示 → 再注销 → 再登录。
- **教务登录 / 成绩 / 课表（ehall）**：需要账号或按业务粘贴 Cookie，凭据只能由用户在本机应用界面输入；我只负责核对结果（会话长度不回显、磁盘无明文、只读第一页、过期与无权限分开报）。

### 36.3 F24：Linux 明文密码兜底静默成功，文档只承诺加密（P1）

### 37.1 F23：预约的服务端写端点已删除

### 37.2 F24：凭据不再退回明文文件（范围比复核时判断的更大）

- **复核时低估了**：不只是 Linux。`keyring_windows.go` 在拿不到用户目录时也会写
  `fileStore{path: "credentials.json"}`——一个**相对路径**的明文文件。
- **做法**：删掉 `fileStore` 整个类型；新增 `store_unavailable.go`：
  `ErrStorageUnavailable` + `unavailableStore`（Save / Load 一律报错，`Describe()` 如实说明
  「系统安全存储不可用（原因），不使用明文文件」）。Linux 无 `secret-tool` 或写入失败 → 报错；
  Windows 拿不到用户目录 → 报错。与会话存储（`unavailableSessionStore`）终于是同一个标准，
  `store.go` 的包注释也去掉了「Linux 没有就退化成权限受限的文件」那句。
- **Delete 的取舍**：`Delete()` 仍然会删掉老版本可能留下的明文 `credentials.json`，
  因此可以如实报成功——没有密钥环时，明文文件就是密码唯一可能存在的地方。
  修好新路的同时不把旧坑留在用户盘上。
- **调用方已核对**：CLI `config set` 走 `fail(err)`（`main.go:531-534`）；
  桌面端 `POST /api/credential` 返回 500 且带错误文本（`server.go:635-637`），
  前端显示「认证已成功，但保存凭据失败：…」。不存在"报错了但界面说成功"的路径。
- **TDD 记录**：先放一个 `Save` 返回 nil 的桩，测试报
  **「没有密钥环时 Save 竟然报成功」**（红），实现后转绿；遗留明文清理那条同样先看它红
  （「删除不该失败：系统安全存储不可用…」）再实现。
- **已知局限（如实）**：Linux 的 `Load()` 仍分不清「密钥环里没这一条」和「密钥环被锁 / 服务没起来」，
  两种都当成没保存过。macOS 那边 R06 已按退出码区分，Linux 还没有可靠依据，**不猜**。

## 38. 发布说明接上 CHANGELOG 单一来源（2026-09-22，未发布）

**起因**：用户问「每次更新并推送的时候会在 release 写清楚更新说明吗」。查线上实际情况：

- **beta0.7 的 Release 正文只有一行**：`**Full Changelog**: https://github.com/Alakazamc/szudesktop/compare/beta0.6.1...beta0.7`（88 字节，链接还指向转移前的旧组织名）。
- beta0.7.1 有 1590 字节的完整说明——那是发完之后用 `gh release edit --notes` **手写**的，不是 CI 生成的。

所以答案是**不会自动写清楚**。`release.yml` 的 release job 里只有 `generate_release_notes: true`，
而 GitHub 的自动生成靠 PR 标题与标签；本项目一直直接提交 main、没有 PR，它就只能吐一个 compare 链接。
仓库里也没有 `.github/release.yml`（那个文件同样只对 PR 分类），`make_release.py` 不生成任何说明文字。
**写不写说明，取决于当次有没有人记得**——beta0.7 就是没记得的那次。

**做法**：

1. 新增根目录 `CHANGELOG.md` 作为发布说明的唯一来源。已回填 beta0.6.1 / beta0.7 / beta0.7.1 三节
   （beta0.7.1 用线上正文原文，beta0.7 按第 31.4 节补记并注明是事后补记），当前批次写在 `## 未发布`。
2. 新增 `desktop/release_notes.py`：按版本号抽取对应小节，再拼上自动生成的下载清单。
   四种情况直接失败——没有这一节、正文为空、正文只有空白、正文里留着 `__VERSION__`；
   另外拒绝把「未发布」当版本号发布。抽取只认**完全相等**的标题，`beta0.7` 不会命中 `beta0.7.1`。
3. `release.yml` 的 release job 补 `checkout` + `setup-python`，先抽取写 `$RUNNER_TEMP/notes.md`，
   再作为 `body_path` 传给 action。**抽取失败就一个附件都不会上传。**
   保留 `generate_release_notes: true`：action 文档写明「提供了 body 时，body 在前、
   自动生成的内容追加在后」，所以 compare 链接仍会自动补上。
4. `make_release.py` 打包前调同一个校验。VERSION 一升、CHANGELOG 忘了写，
   **PR 阶段的 windows job 就会红**，不用等到打 tag 才发现。
5. 标签名不在 `run:` 里直接插值 `${{ }}`，改走 `env:`，避免成为脚本注入面。

**TDD**：先写 `desktop/check_release_notes.py`（11 项），跑出 `ModuleNotFoundError: release_notes`（红），
再实现模块转绿。

### 39.4 F26：部分 macOS 上凭据存不进去（P0，只有真机能抓到）

run 35627181165 的探针日志（真实 macOS runner）：

```
+ security add-generic-password -a probe -s szunet-selftest-probe -U -w
password data for new item: retype password for new item: passwords don't match
+ security find-generic-password -a probe -s szunet-selftest-probe -w
security: SecKeychainSearchCopyNext: The specified item could not be found in the keychain.
##[error]Process completed with exit code 44.
```

- **成因**：`security -w` 放末尾时会要求**输入两遍**（`password data for new item` 与
  `retype password for new item`），而 F21 的 `secretInput` 只喂了一行。
  第二遍读到空 → 两次不一致 → 条目根本没建起来。
- **这个行为不稳定，必须如实记**：同一镜像 `macos-26-arm64` / macOS 26.6.2 (25G83) 的
  后续 4 次运行，探针都记录为「只喂一行也能写入（没有要求确认）」。
  也就是说**问不问第二遍因机器/时刻而异**，所以探针只把它当记录、不当断言。
- **影响**：在会要求确认的机器上，`keychainSave` 的写前自检必然失败，于是 macOS 上
  `szunet config set` 与桌面端保存凭据 / 会话全部报错。设计上的「宁可失败也不退回 argv」生效了，
  所以**没有泄漏、也没有明文落盘**，但功能是坏的。
  **beta0.7.1 与 beta0.7.2 都带着这个缺陷**——在会要求确认的 macOS 上，
  F21 那个安全修复从来没真正可用过。
- **修复**：`secretInput` 改为喂「密码 + 确认」两行。只问一遍的机器上多出的那行
  只是没人读的剩余输入——**这一点已由真机验证**（见 39.5），不再是推测。
- **TDD 记录**：先把两个测试替身改成如实模拟两次提问（可移植的 `fakeKeychain`
  与 unix 版真 exec 的假脚本），5 个既有测试立刻变红，错误信息与真机日志**一字不差**
  （`exit status 44（passwords don't match）`）；再改 `secretInput` 转绿。
  新增 `TestKeychainWriteFeedsSecretTwiceForConfirmation` 直接断言 stdin 是两行且一致。
  这条性质现在本地与 Linux CI 都守得住，不必依赖 macOS。

## 41. 修「场地与琴房规则速查」带出来的渲染链路缺陷，以及命令行开机自启（2026-09-22，未发布）

复核 `34c5d57`（场地规则速查）时发现：这个功能本身是对的，但它把一组**新的失败模式**
引进了渲染链路。同时首轮就记下的 F27（命令行开机自启）仍在。本轮一并修掉。

### 41.1 渲染链路上的静默失败（P2-8 / P2-9）

- **P2-8**：`openHours()` 要对学校的 64 位 `availableTimePeriod` 做位运算，而 JS 的位运算会在
  32 位截断，只能用 BigInt。原实现遇到非整数、带千分位的字符串、超出 `Number.MAX_SAFE_INTEGER`
  的值都会抛异常；而它在 `services()` 里被无条件求值，结果整段赋给 `#main`。
  **一旦抛出，那句赋值就不执行 —— 整个「校园服务」页静默不更新，且不向用户报任何错。**
  现在不可信输入一律降级成「—」，函数本身绝不抛。
- **P2-9**：分组键原来是类型 `name`。不同类型重名时会把两类场地并成一组，并顺手用第一个场地的
  规则去描述另一类 —— 规则张冠李戴比不显示更糟。改用场地自带的 `typeId`。
- **另外补了两层兜底**：`services()` 里每张卡片各自 try/catch（坏掉一块只降级这一块），
  `render()` 里由 `pageHTML()` 兜底（整个页面函数抛异常时换成一页可读提示，而不是留空白，
  也不打断 `clocks()`）。原来的设计是「一处异常 → 整页白板 + 无提示」，这两层把爆炸半径收掉了。

### 41.2 两条读取路径的校验强度对齐（P2-10）

`availability` 一直校验 `Mask>>48`、单日上限、可提前天数；新出现的 `/booth/list` 路径没校验，
于是同一份数据「空位查询会拒绝、规则卡片照单全收」。把边界收成 `bookingType.validate()` 两处共用。

**但列表路径只收敛、不整份拒绝**：`availability` 用掩码决定显示哪些时段，掩码错一格就是错数据，
必须硬失败；列表只用 type 展示规则，为一个场地字段异常扣下整份列表会让用户什么都看不到。
所以列表路径把越界数字折成零值（前端显示「—」，等于如实说「这项未知」），场地本身照旧出现。

### 41.3 学校富文本的块级标签（P2-11）

`plainTextFromSchoolHTML` 原来只把 `</p>` `</li>` 换成换行，`<br>` 还只认小写三种写法。
学校改用 `div` / `h3` / `tr` 排版时整段须知会被挤成一行，`<!-- -->` 注释也会原样混进正文。
现在补齐块级结束标签（含表格与标题）、大小写与自闭合的 `<br>`，并丢掉注释。

### 41.4 同一份数据被打两遍（P2-12）

规则卡片与空位卡片各自请求 `/api/booking/rooms`。抽出 `createRoomsLoader(api, ttl)`：
带短 TTL、合并并发调用、**失败不写缓存**，两张卡片共用一份。只在前端共享，不为此给 Go 侧引入
并发状态 —— 这里要的是「两次点击打一次接口」，前端一次就够，给服务端加缓存只会让失效时机变复杂。
见 41.6：41.4 的原始分析是在没有 Go 工具链的前提下写的，本轮已补装并完整跑过编译与测试。

### 41.5 命令行开机自启（F27）

旧启动项不改注册表就能恢复。详情见 F27 行。

### 42.2 他修的第一个问题：我引入的渲染静默失败

**问题是我造成的。** `booking.mjs` 里的 `openHours()` 写的是 `BigInt(m||0)`：
学校返回的 `availableTimePeriod` 一旦是带千分位的字符串、小数、或超出 `Number.MAX_SAFE_INTEGER`，
这行就抛异常；而它在 `services()` 里被**无条件求值**，结果整段赋给 `#main`。
异常一抛，那句赋值就不执行——**整个「校园服务」页静默停止更新，用户看不到任何提示**。

我在真机验证时用的是正常值（`4397794590720`），所以没触发。**这个 bug 只在字段格式异常时现形**，
学校改一次字段格式就能让整页变白板。为了显示一个"开放 10 小时"赌上整页渲染，代价和收益完全不成比例。

**修法**（我认可）：
- `openHours` 与新增的 `ruleNum` 一律不抛，不可信输入降级成「—」
- `ruleNum` 用 `Number.isSafeInteger` 而非 `isFinite`——同时挡住小数、`Infinity`、`NaN`、超安全整数
- **0 也显示「—」**：服务端会把越界值收敛成 0（见 `bookingType.validate`），
  分不清「学校真报了 0」和「我们自己清零的」，宁可标成未知，也不拿 0 冒充学校数字
- 分组键从类型 `name` 改为 `typeId`：name 是展示字符串，两类重名会被并成一组，
  并顺手用第一个的规则描述另一类——规则张冠李戴比不显示更糟
- 两条读取路径**故意用不同失败策略**：`availability`（掩码决定显示哪些空位）硬失败，
  掩码错一格就是错数据；`/booth/list`（只展示规则）把越界值降级，不为一个场地字段扣下整份列表

### 42.3 他修的第二个问题：F27 命令行版开机自启静默失效

`internal/autostart/autostart_windows.go` 里命令行版开机自启登记的是 `szunet login --auto`，
而 `login` **从来没有 `--auto` 这个参数**；szunet 的 flag 集是 `ExitOnError`，遇到未知开关直接 `os.Exit(2)`。
**所以开过这个开关的用户，开机时程序什么都没做就退出了，且没有任何报错。**

失败只反映在退出码上），抽成 `CLILoginArgs()` 常量避免三处各写各的；

**他是先复现再修的**：从 `34c5d57` 单独编出 CLI 做对照，`login --auto` 得到退出码 2 与

这是实证，不是看代码猜。
